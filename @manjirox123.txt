# 5. SECURITY AND AUTHORIZATION MODEL

The product is a professional security-testing platform.

The system must assume that testing is performed against systems the user is authorized to test.

However, the software itself must implement safety boundaries.

Create a central:

```text
Security Test Policy
```

with the following modes:

### MODE 1 — PASSIVE

Safe by default.

Allowed:

* observe traffic
* parse traffic
* decode traffic
* classify traffic
* analyze headers
* inspect cookies
* inspect TLS metadata
* identify technologies
* identify potential security issues
* analyze authentication flows
* analyze API structure
* generate suggestions
* generate reports

No mutated requests are automatically transmitted.

### MODE 2 — MANUAL ACTIVE

The user explicitly sends a modified request.

Examples:

* editing parameters
* changing headers
* changing body
* replaying a request
* comparing responses
* sending a manually selected request

### MODE 3 — AUTHORIZED TESTING

The user explicitly defines an allowlist of hosts/domains.

Active test modules may operate only against the allowlisted targets.

Implement:

```text
Allowed Hosts
Allowed Ports
Allowed Schemes
Allowed Paths
Excluded Hosts
Excluded Paths
Request Rate Limit
Concurrency Limit
Maximum Requests
Maximum Body Size
Maximum Response Size
Timeout
Maximum Test Duration
```

### MODE 4 — LAB

Designed for:

* localhost
* 127.0.0.1
* private development environments
* intentionally vulnerable labs
* local containers
* test virtual machines

Allow more automation.

### MODE 5 — DANGEROUS-ACTION CONFIRMATION

Any operation classified as destructive, intrusive, credential-changing, account-changing, resource-consuming, or potentially disruptive must require an explicit user action before execution.

AI must never silently escalate itself from passive analysis into unrestricted active testing.
